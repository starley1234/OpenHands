# Сервисы (mini-frontends) — независимые приложения поверх единого бэкенда

Здесь живут **независимые сервисы** — маленькие, заточенные под одну функцию
приложения (например «написать книгу и опубликовать её как сайт»). Каждый
сервис — это самодостаточный пакет в собственной папке (`services/<имя>/`) со
своим:

- **конфигом сервиса** (`config.json`) — какие скиллы, MCP-серверы, модель и
  сценарий/промпт использовать, на каком порту публиковаться;
- **прослойкой-бэкендом сервиса** (`server.mjs`) — тонким шлюзом, который
  говорит с **единым бэкендом** (agent-server) и отдаёт готовый результат;
- **тонким фронтендом** (`web/`) — голый минимальный UI, который общается
  только со своим сервисом, а не с единым бэкендом напрямую.

## Архитектура

```
┌──────────────┐   HTTP   ┌──────────────────────┐
│ Тонкий        │ ──────► │ Прослойка-сервис      │   config.json:
│ фронтенд      │         │ (server.mjs)          │   skills, mcp, model,
│ (web/)        │ ◄────── │  · настройки сервиса  │   scenario, port
└──────────────┘         │  · публикует статику   │
                         └──────────┬─────────────┘
                                    │ REST (создание диалога,
                                    │ статус, файлы проекта)
                                    ▼
                         ┌──────────────────────┐
                         │  ЕДИНЫЙ БЭКЕНД        │  (agent-server, неизменный)
                         │  agent-server +       │
                         │  automation + Canvas  │
                         └──────────────────────┘
```

Ключевые принципы:

1. **Единый бэкенд остаётся единственным источником правды** про агента: он
   выполняет диалоги, держит MCP/скиллы, работает с файлами. Ничего не
   форкаем и не дублируем.
2. **Прослойка-сервис** инкапсулирует *настройки конкретной функции*: какой
   сценарий дать агенту, какие скиллы/MCP включить, на каком порту отдавать
   результат. Она — единственный, кто знает детали; фронтенду их знать не нужно.
3. **Тонкий фронтенд** — максимально простая страница «введите тему → получите
   результат». Он не ходит в agent-server напрямую (не тащит API-ключи,
   настройки, конфиденциальность бэкенда).
4. **Независимость**: каждый сервис можно запускать/останавливать отдельно,
   разворачивать на своём порту (диапазон 8290–8300 уже проброшен в Docker),
   обновлять без влияния на остальные.

## Структура одного сервиса

```
services/<имя>/
  config.json      # скиллы, mcp, модель, сценарий, порт (читает server.mjs)
  server.mjs       # прослойка: слушает свой порт, зовёт единый бэкенд, отдаёт статику
  web/             # тонкий фронтенд (HTML/JS/CSS, собирается при желании отдельно)
  out/             # (генерируется) публикуемый результат, например статический сайт
  Dockerfile       # (опционально) отдельный контейнер для независимого деплоя
  README.md        # что за функция, как запустить
```

## Контракт прослойки (обязательные endpoints)

Каждый `server.mjs` реализует единый набор маршрутов, чтобы управление было
предсказуемым:

| Маршрут | Описание |
| --- | --- |
| `GET  /` | тонкий фронтенд |
| `GET  /health` | живой ли сервис |
| `POST /api/run` | создать/запустить сценарий (тело: входные данные пользователя) |
| `GET  /api/status` | статус текущей задачи (running / finished / error) |
| `GET  /api/result` | готовый результат (например список глав / ссылку на сайт) |
| `GET  /out/*` | опубликованная статика (сгенерированный сайт) |

Прослойка общается с единым бэкендом через его REST API (создание диалога
`POST /api/conversations`, опрос статуса, чтение файлов проекта), скрывая
детали от фронтенда.

## Как запустить любой сервис

Каждый сервис — самостоятельный Node-процесс на своём порту (8290–8300 уже
проброшены в Docker). Из корня репозитория:

```bash
# 1. Подними единый бэкенд (если ещё не поднят)
docker compose up -d --build

# 2. Запусти прослойку нужного сервиса (или все сразу через services/run.sh)
cd services/<имя>
AGENT_SERVER_URL=http://localhost:8000 \
AGENT_SERVER_API_KEY=<LOCAL_BACKEND_API_KEY> \
node server.mjs

# 3. Открой http://localhost:<порт>/
```

Или одной командой запустить всё:

```bash
./services/run.sh              # все сервисы
./services/run.sh book-site    # один
```

`AGENT_SERVER_URL`/`AGENT_SERVER_API_KEY` указывают на единый бэкенд. Хелпер
`services/lib/agent-server.mjs` забирает настройки агента с бэкенда
(`GET /api/settings` с зашифрованными секретами), создаёт диалог и опрашивает
его статус — так сервис не дублирует LLM-ключи и настройки.

Пути: бэкенд видит рабочую директорию как `/projects/...`, сервис читает те же
файлы на хосте как `./projects/...`. Маппинг задаётся `AGENT_WORK_ROOT` (по
умолч. `/projects`) и `HOST_WORK_ROOT` (по умолч. `<корень>/projects`).

## Как добавить новый сервис

1. Скопируйте `services/book-site/` как заготовку в `services/<имя>/`.
2. Заполните `config.json` (скиллы, MCP, модель, сценарий, порт).
3. В `server.mjs` используйте `../lib/agent-server.mjs`: `startConversation`
   (создаёт диалог на едином бэкенде с вашим сценарием) + `getConversationStatus`
   (опрос статуса). Опишите, как из входных данных пользователя собрать/опубликовать
   результат (обычно — прочитать файлы из рабочей директории и собрать статик-сайт в `out/`).
4. Положите тонкий фронтенд в `web/`.
5. Дайте сервису свободный порт в диапазоне 8290–8300 (уже открыт в `docker-compose.yml`).

## Зачем так, а не «вкладки внутри Canvas»

- **Изоляция настроек**: у каждой функции свой сценарий/скиллы/MCP, не
  пересекаются с основным чатом.
- **Голый фронтенд**: юзеру не нужен весь Canvas, чтобы получить книгу или
  сайт — только минимальная страница функции.
- **Независимый деплой**: сервис можно хостить отдельно, масштабировать и
  обновлять самостоятельно.
- **Корень не захламляется**: все мини-приложения лежат в `services/`, в
  репозитории есть один общий паттерн вместо разрозненных папок в корне.
