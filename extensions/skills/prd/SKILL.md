# Генератор PRD

Создавай подробные документы требований к продукту (PRD), которые ясны, применимы на практике и готовы к реализации.

---

## Задача

1. Получить от пользователя описание функции
2. Задать 3-5 ключевых уточняющих вопросов (с вариантами ответов по буквам)
3. Сгенерировать структурированный PRD на основе ответов
4. Сохранить в `prd-[имя-функции].md` в корне репозитория

**Важно:** НЕ начинай реализацию. Просто создай PRD.

---

## Шаг 1: Уточняющие вопросы

Задавай только критические вопросы, где исходный запрос неоднозначен. Сфокусируйся на:

- **Проблема/Цель:** Какую проблему это решает?
- **Основная функциональность:** Какие ключевые действия?
- **Границы/Объём:** Чего оно НЕ должно делать?
- **Критерии успеха:** Как мы поймём, что готово?

### Формат вопросов:

```
1. Какова основная цель этой функции?
   A. Улучшить онбординг пользователя
   B. Повысить удержание пользователей
   C. Снизить нагрузку на поддержку
   D. Другое: [уточните]

2. Кто целевой пользователь?
   A. Только новые пользователи
   B. Только существующие пользователи
   C. Все пользователи
   D. Только администраторы

3. Каков объём?
   A. Минимальная рабочая версия
   B. Полнофункциональная реализация
   C. Только бэкенд/API
   D. Только интерфейс
```

Это позволяет пользователю отвечать «1A, 2C, 3B» для быстрой итерации. Помни про отступы для вариантов.

---

## Шаг 2: Структура PRD

Сгенерируй PRD со следующими разделами:

### 1. Введение/Обзор
Краткое описание функции и проблемы, которую она решает.

### 2. Цели
Конкретные, измеримые задачи (маркированный список).

### 3. Пользовательские истории
Каждая история должна содержать:
- **Название:** Короткое описательное имя
- **Описание:** «Как [пользователь], я хочу [функцию], чтобы [выгода]»
- **Критерии приёмки:** Проверяемый чек-лист того, что значит «готово»

Каждая история должна быть достаточно малой, чтобы реализовать её за одну сфокусированную сессию.

**Формат:**
```markdown
### US-001: [Название]
**Описание:** Как [пользователь], я хочу [функцию], чтобы [выгода].

**Критерии приёмки:**
- [ ] Конкретный проверяемый критерий
- [ ] Ещё один критерий
```

**Важно:**
- Критерии приёмки должны быть проверяемыми, а не расплывчатыми. «Работает корректно» — плохо. «Кнопка показывает диалог подтверждения перед удалением» — хорошо.
- Фокусируйся на том, *что* должна делать функция, а не на том, как её проверять при разработке (например, шаги линтера/тайпчека относятся к «Определению готово», а не к критериям приёмки PRD).

### 4. Функциональные требования
Нумерованный список конкретных функций:
- «FR-1: Система должна позволять пользователям...»
- «FR-2: Когда пользователь нажимает X, система должна...»

Будь явным и однозначным.

### 5. Не-цели (вне объёма)
Что эта функция НЕ будет включать. Критично для управления объёмом.

### 6. Проектные соображения (опционально)
- Требования к UI/UX
- Ссылки на макеты, если есть
- Существующие компоненты для переиспользования

### 7. Технические соображения (опционально)
- Известные ограничения или зависимости
- Точки интеграции с существующими системами
- Требования к производительности

### 8. Метрики успеха
Как будет измеряться успех?
- «Сократить время выполнения X на 50%»
- «Повысить конверсию на 10%»

### 9. Открытые вопросы
Оставшиеся вопросы или области, требующие уточнения.

---

## Написание для начинающих разработчиков

Читателем PRD может быть начинающий разработчик или ИИ-агент. Поэтому:

- Будь явным и однозначным
- Избегай жаргона или объясняй его
- Давай достаточно деталей для понимания цели и основной логики
- Нумеруй требования для удобства ссылок
- Используй конкретные примеры там, где это полезно

---

## Вывод

- **Формат:** Markdown (`.md`)
- **Имя файла:** `prd-[имя-функции].md` (kebab-case)

---

## Пример PRD

```markdown
# PRD: Система приоритетов задач

## Введение

Добавить уровни приоритета задачам, чтобы пользователи могли сосредоточиться на самом важном. Задачи можно помечать как высокий, средний или низкий приоритет, с визуальными индикаторами и фильтрацией, помогающими эффективно управлять нагрузкой.

## Цели

- Разрешить присвоение приоритета (высокий/средний/низкий) любой задаче
- Обеспечить чёткое визуальное различие между уровнями приоритета
- Включить фильтрацию и сортировку по приоритету
- По умолчанию новые задачи получают средний приоритет

## Пользовательские истории

### US-001: Добавить поле приоритета в базу данных
**Описание:** Как разработчик, мне нужно хранить приоритет задачи, чтобы он сохранялся между сессиями.

**Критерии приёмки:**
- [ ] В таблице задач существует колонка приоритета с типом 'high' | 'medium' | 'low' (по умолчанию 'medium')
- [ ] Значения приоритета корректно сохраняются при перезапуске приложения

### US-002: Показывать индикатор приоритета на карточках задач
**Описание:** Как пользователь, я хочу видеть приоритет задачи с первого взгляда, чтобы понимать, чему уделить внимание в первую очередь.

**Критерии приёмки:**
- [ ] Каждая карточка задачи показывает цветной бейдж приоритета (красный=высокий, жёлтый=средний, серый=низкий)
- [ ] Приоритет виден без наведения или клика

### US-003: Добавить выбор приоритета при редактировании задачи
**Описание:** Как пользователь, я хочу менять приоритет задачи при её редактировании.

**Критерии приёмки:**
- [ ] Выпадающий список приоритета в модальном окне редактирования задачи
- [ ] Показывает текущий приоритет как выбранный
- [ ] Сохраняется сразу при изменении выбора

### US-004: Фильтровать задачи по приоритету
**Описание:** Как пользователь, я хочу фильтровать список задач, чтобы видеть только высокоприоритетные, когда я сосредоточен.

**Критерии приёмки:**
- [ ] Выпадающий список фильтра с вариантами: Все | Высокий | Средний | Низкий
- [ ] Фильтр сохраняется в параметрах URL
- [ ] Сообщение о пустом состоянии, когда ни одна задача не подходит под фильтр

## Функциональные требования

- FR-1: Добавить поле `priority` в таблицу задач ('high' | 'medium' | 'low', по умолчанию 'medium')
- FR-2: Показывать цветной бейдж приоритета на каждой карточке задачи
- FR-3: Включить выбор приоритета в модальное окно редактирования задачи
- FR-4: Добавить выпадающий список фильтра приоритета в заголовок списка задач
- FR-5: Сортировать по приоритету в пределах каждой колонки статуса (от высокого к низкому)

## Не-цели

- Без уведомлений и напоминаний на основе приоритета
- Без автоматического присвоения приоритета по сроку
- Без наследования приоритета для подзадач

## Технические соображения

- Переиспользовать существующий компонент бейджа с вариантами цветов
- Состояние фильтра управляется через параметры URL
- Приоритет хранится в базе данных, не вычисляется

## Метрики успеха

- Пользователи могут изменить приоритет менее чем за 2 клика
- Высокоприоритетные задачи сразу видны в верхней части списков
- Нет регресса в производительности списка задач

## Открытые вопросы

- Должен ли приоритет влиять на порядок задач в пределах колонки?
- Нужно ли добавить горячие клавиши для изменения приоритета?
```

## Чек-лист

Перед сохранением PRD:

- [ ] Заданы уточняющие вопросы с вариантами по буквам
- [ ] Учтены ответы пользователя
- [ ] Пользовательские истории малы и конкретны
- [ ] Функциональные требования пронумерованы и однозначны
- [ ] Раздел не-целей задаёт чёткие границы
- [ ] Сохранено в `prd-[имя-функции].md`
